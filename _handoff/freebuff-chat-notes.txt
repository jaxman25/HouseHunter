7. RISKS / BREAKING CHANGES

- F3 (storage rules) is the highest-risk: tightening rules denies future writes only (existing objects unaffected), but any legit upload with an unexpected content-type (e.g., HEIC picked directly on iOS if the picker doesn't transcode — worth verifying against  IMAGE_CONFIG.allowedTypes  which excludes HEIC) would start failing. Must confirm what content-type the picker actually produces per platform before setting the allowlist.
- F5 (CSP tightening) risks breaking the web build outright if the bundle uses eval/inline styles-at-runtime; must be validated with  npm run build:web  + browser smoke test before adoption.  public/index.html 's inline script requires either  'unsafe-inline'  or a hash until moved external (F5a).
- F1/F2 change user-visible behavior: oversized/non-image files that "worked" before will now be rejected.
- F4 could interfere with  <img>  rendering only if applied to sources used in  img src  —  Content-Disposition: attachment  affects top-level navigation, not image embeds, so risk is low, but should be applied to export JSONs primarily (already signed-URL downloads).
- Regex sanitizers ( removeDangerousHtml ) are bypassable in principle (mutation/nesting tricks) — they must not be relied upon if an HTML-rendering surface is ever added (ties to F7).
